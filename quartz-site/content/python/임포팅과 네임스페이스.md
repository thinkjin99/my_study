### 파이썬 임포팅의 동작 방식

파이썬의 임포팅은 단순히 특정한 모듈을 참조하는 행위가 아니다. 엄밀히 말하자면 **특정한 모듈을 로딩하고 이를 네임스페이스에 등록하는 과정**이 import 코드가 실행될때 이뤄진다.

임포팅은 다음의 순서를 거쳐 진행된다.

```markdown
import some_module
    ↓
[1] sys.modules 캐시 확인
    ↓
[2] 캐시에 없으면 sys.path 경로 탐색
    ↓
[3] some_module.py (또는 .pyc 등) 발견
    ↓
[4] 모듈 코드 전체 실행 (탑 레벨만)
    ↓
[5] 모듈 객체 생성 → sys.modules['some_module'] 에 저장
    ↓
[6] 다른 곳에서 import 시 재사용 (실행 안 됨)
```

파이썬은 우선적으로 참조하는 모듈이 이미 캐싱돼 있는지를 확인한다. 캐싱의 여부는 이미 모듈이 로딩돼 `sys.modules` 라는 전체 모듈 객체를 관리하는 딕셔너리에 존재하는지를 확인하는 과정이다. **파이썬의 모든 것은 객체이기 때문에 모듈 또한 로딩이 되면 객체의 형태로 딕셔너리 내부에서 관리된다.**

만약 해당 모듈이 딕셔너리 내부에 없을 경우 파이썬은 파이썬 바이트코드인 `.pyc`파일 혹은 원본 스크립트 파일을 탐색한다. 이후 해당 ==**스크립트에 정의된 코드를 실행**==하고 이를 객체로 포장해 `sys.modules`에 저장한다. 

여기서 흥미로운 점은 모듈에 존재하는 코드를 실행한다는 점인데, 모듈 객체를 정의 하려면 인터프리터가 모듈의 코드를 실행 해야하고 이때 탑 레벨의 코드가 실행되는 현상이 발생한다.

예를 들어 이러한 코드를 확인해보자. 

```python title:a.py
def foo():
	print("Hi")

print("This is module a")
```

그리고 이를 모듈로 임포팅하는 다음과 같은 모듈이 있다고 해보자.

```python title:b.py
import a
print("This is module b")
```

코드를 실행해보면 모듈 a와 b가 전부 출력되는걸 확인할 수 있다. 왜 이렇게 동작하는 걸까?

> [!info]
> 파이썬에서 모듈을 임포트하기 위해 반드시 실행이 필요한 이유는, **파이썬이 모든 것을 객체로 다루는 언어**이기 때문이다. 함수, 클래스는 물론 모듈 자체도 하나의 객체이며, 이를 사용하려면 인터프리터가 해당 `.py` 파일의 코드를 실행해 그 결과로 모듈 객체를 만들어 메모리에 올리는 과정이 필요하다. 
즉, 파이썬에서 무언가를 "정의"한다는 것은 곧 "코드를 실행해서 객체를 생성하는 것"을 의미하며, 정의와 실행이 분리될 수 없다.

==반면 C 언어에서는 참조할 **코드가 이미 컴파일되어 기계어로 변환된 상태**이며, 실행 시점에는 해당 코드의 메모리 주소를 따라 점프하면 그만==이다. 정의는 컴파일 시점에 완료되고, 링커가 심볼을 통해 연결을 마치므로 실행 시에 따로 정의를 위한 동작은 필요하지 않다. 

>[!info]
>파이썬은 모든 것이 객체이기에 런타임에 모든 작업을 수행해야 한다. 따라서 무언가를 정의하기 위해서도 실행을 진행해야만 한다.


우리는 이제 모듈이 특정한 객체의 형태로 존재하고 파이썬은 이러한 모듈 인스턴스를 만들기 위해서 모듈 내부의 스크립트를 실행한다는 것을 확인했다. 그렇다면 이 인스턴스는 어디에 저장되는 걸까? 어딘가에 저장 돼야 참조와 캐싱이 가능하지 않을까?

파이썬은 모듈 객체를 2곳에 저장한다. 

#### sys.modules
**모듈을 관리하는 객체로 인터프리터마다 존재한다.**  하나의 인터프리터는 프로세스마다 존재하기에 파이썬 프로세스는 하나의 `sys.modules`를 공유한다. 만약 프로세스 내부에서 모듈의 참조가 발생하면 무조건 해당 객체를 통해 참조가 이뤄지고 이를 기반으로 캐싱도 진행된다.
실질적으로 파이썬에서 `import` 구문의 의미는 `sys.modules`에 대입하는 것과 동일하다.

```python
import foo

# 이는 곧
foo = sys.modules["foo"]
# 이제 foo를 접근하면 sys.modules로 접근한다.
# foo는 곧 sys.modules에 대한 참조이다
```

즉 우리가 임포팅을 진행하면 이미 로딩된 모듈의 경우 캐싱된 데이터를 반환하고 아닐 경우 딕셔너리에 저장하고 참조를 반환하는 작업을 수행해준다.

### 임포팅한 네임스페이스
모듈을 참조할 때는 모두 `sys.modules`를 통한다고 했지만, 일반적으로 파이썬에서의 참조는 단순히 모듈명을 나열하는 것만으로 가능하다. 이를 가능케 위해서는 모듈명과 실제 모듈 인스턴스의 매핑을 진행해주는 요소가 필요한데 이를 네임스페이스를 통해 수행한다. 네임스페이스는 말 그대로 이름 공간으로 이름과 실제 객체를 매핑하는 작업을 수행한다.
**파이썬에서 모듈을 임포팅하면 해당 모듈명이 네임스페이스에 등록되며 `sys.modules`와 매핑된다. 이에 따라서 손쉽게 모듈명만으로 참조가 가능해진다.**

>[!info]
>파이썬에 모듈을 임포팅하면 모듈 인스턴스가 생성되고 이후 이는 sys.modules에 저장된다. 저장된 모듈 객체는 네임스페이스에서 모듈명과 매핑되며 이를 통해 이름만을 통한 참조가 가능해진다.

### 파이썬 모듈 임포팅 경로

파이썬이 임포팅한 모듈을 `sys.modules`를 통해 관리한다는 것은 학습했다. 이제 파이썬이 임포팅할 모듈을 어떻게 탐색하는지를 생각해보자. 파이썬이 임포팅할 파일을 탐색하는 방식은 다음과 같다. 

1. 현재 파이썬 스크립트가 존재하는 디렉토리 탐색
2. 환경변수 PYTHONPATH에 저장된 디렉토리
3. 표준 라이브러리 경로
4. 서드파티 패키지 경로

이러한 모듈 탐색 경로는 전부 `sys.path` 내부에 저장돼 있으며 해당 데이터를 기반으로 모듈의 탐색을 진행한다. 

파이썬을 작성하다보면 상위 폴더에 있는 모듈의 참조가 어려워서 골치 아파 본적이 있을 법한데 이 문제 또한 위의 모듈 탐색 방식을 이해하고 보면 간단히 해결 가능하다.

이러한 폴더 구조를 생각해보자. 

```bash
path_test
	parent.py
	child/
		child.py
```

이때 `child.py`에서 `parent.py`의 함수를 참조해 활용하는걸 생각해보자. 스크립트 내용은 아래와 같다.

```python

#child.py
import sys
print(sys.path)

from .. import parent
parent.parent()

#parent.py
def parent():
	print("this is parent")

```

`/child`의 위치에서 코드를 실행하면 다음과 같은 오류가 발생한다. 

```Traceback (most recent call last):

from .. import parent
ImportError: attempted relative import with no known parent package
```

이러한 에러가 발생하는 이유는 간단한데 파이썬의 실행위치에서 알맞지 않은 참조를 통해 모듈을 임포팅하기 때문이다. 이때 파이썬의 실행 경로를 확인해보면 다음과 같다.

```
['/Users/myoungjin/programming/path_test/child', '/opt/homebrew/Cellar/python@3.13/3.13.3/Frameworks/Python.framework/Versions/3.13/lib/python313.zip', '/opt/homeb

```

경로에 앞서 말한 스크립트의 현재 디렉토리나 파이썬 확장 경로 써드파티 패키지들이 포함 되지만 상위 폴더에 대한 경로는 존재하지 않는다. 이에따라서 상대경로 참조를 활용해 상위 모듈 접근을 시도할 경우 문제가 발생한다.

>[!info]
> 이러한 문제는 파이썬에서 상대경로를 활용한 참조를 수행하다보면 자주 발생하는 이슈인데 이에 따라서 파이썬에서는 되도록 절대경로를 기반으로한 참조를 권장한다. (루트 디렉토리를 기준으로 참조를 진행하는 방식이다.)

### 패키지와 `__init__`

패키지는 모듈의 집합을 의미한다. 즉 여러 모듈이 존재하는 폴더가 곧 패키지가 된다. 패키지의 효능과 배경을 알려면 역사를 알아햐는데 3.3버전 이전의 파이썬은 `__init__.py` 파일이 존재하지 않는 디렉토리에 존재하는 모듈을 임포팅하는 것이 불가능했다. 

이는 해당 디렉토리가 참조할 모듈이 존재하는지 아니면 단순 리소스 폴더인지 구분하는 것이 어려웠기 때문인데 3.3 이후부터는 `__init__.py`가 없어도 특정한 디렉토리에 모듈이 존재할 경우 패키지로 인식하는 것이 가능해졌다.

패키지로 인식한다는 행위는 곧 해당 디렉토리의 이름을 따서 모듈 객체를 생성하고 이를 기반으로 참조를 진행하는 것을 가능케 하는 것을 말한다. 아래의 경우를 살펴보자.

```bash
my_project/
    my_package/
        utils.py
```

`utils.py` 모듈을 참조하고 싶다면 `import my_package.utils` 와 같은 방식으로 참조를 수행할 수 있다. 이는 당연한 사실이지만 사실 처음 패키지에 임포트를 할때 생성된 패키지 모듈 객체를 `sys.modules`에 등록한 뒤에 이를 기반으로 접근하는 방식으로 동작한다. 즉 자동으로 패키지 모듈 객체를 생성하고 이를 기반으로 모듈 참조를 진행한다.

뭐야 이제 자동으로 해주는거 아님 그러면 `__init__.py`는 왜 필요한거지? 라는 생각이 들었다면 아티클을 야무지게 따라오고 계시는 중이다. 해당 파일의 사용 예시는 크게 3가지이다.

#### 임포팅을 깔끔히 하고 싶은 겨우
디렉토리가 중첩되거나 할 경우 임포팅 구문이 끝도 없이 길어지는 경우가 존재한다. 이때 해당 파일에서 미리 임포트 구문을 정의해두면 번잡했던 임포팅을 단축해서 활용할 수 있다. 아래의 경우를 보자.

```python
"""
ml_package/
    __init__.py
    preprocessing/
        __init__.py
        normalize.py

    models/
        __init__.py
        linear.py
"""
#ml_package/__init__.py
from . import preprocessing
from . import models

__all__ = ["preprocessing", "models"]
```

이런 식으로 `__all__`에 하위 모듈의 참조를 미리 입력해두면 이후 참조를 수행할 때는 간단하게 `ml_package.models.~~`와 같은 방식으로 참조 하는게 가능해진다.

> `__all__` 파이썬 모듈이 외부에 드러낼 속성을 정의하는 필드이다 해당 속성에 정의된 값만이 외부 모듈에서 참조 가능하다.

#### 모듈참조 전 선행작업이 필요한 경우
로깅이나 전처리 작업등이 임포팅 전에 수행될 필요가 존재할 경우에도 해당 파일을 활용할 수 있다. 해당 파일은 패키지가 임포팅 될때 최초로 실행된 이후 수행되지 않는 모듈이기 때문에 만약 선결 작업이 필요할 경우 해당 파일에 정의해 활용할 수 있다.

```python
# __init__.py
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)
logger.info("data_tools package initialized")
```


### 몇가지 흑마법
위의 두가지 경우를 제외하고 해당 파일을 정의해서 활용할 일은 보통 없다. 이를 활용하면 몇가지 흑마법이 가능한데 우선적으로 해당 파일을 정의하면 기본 라이브러리를 덮어쓸 수 있다. 예를 들어 `math` 모듈을 참조할 때 기본 라이브러리 모듈이 아니라 현재 로컬에 정의한 `math` 모듈을 우선적으로 임포팅하게 처리하는 것이 가능하다.

이런 작업이 가능한 이유는 해당 파일이 존재할 경우 파이썬이 패키지 모듈 객체를 로컬을 기준으로 덮어써 버리기 때문이다. 다시 말해서 기본 라이브러리에 정의된 패키지 모듈 객체가 아닌 로컬 모듈 객체가 생성되며 이를 재정의 하는 현상이 발생하기 때문에 이와 같은 현상이 발생한다.

>[!info]
>`__init__.py` 파일을 활용하면 로컬 파일 경로를 기반으로 패키지 모듈 객체가 생성된다. 만약 생략할 경우 파이썬이 자체적으로 경로를 지정해 모듈 객체를 생성한다.

### 모듈과 네임 스페이스

모듈 스페이스는 모듈 객체의 범위에서 참조 가능한 변수들의 범위를 나타내는 공간을 의미한다. 파이썬에서 흔히 말하는 전역 공간은 곧 모듈 스페이스와 동일한 의미를 갖는다. 모듈 스페이스는 모듈에 정의된 모든 객체를 참조 가능케 하는 딕셔너리를 의미하며 해당 모듈에서 정의된 객체를 접근하기 위해서는 해당 딕셔너리가 활용된다.

아래의 코드를 살펴보자.

```python
#test.py
a = 5
b = a + 1

def foo():
	c = a + 2
	
```

a, b, c는 각각 어떻게 참조를 진행해서 값을 생성하는 걸까? 먼저 우리가 a를 생성할 경우 해당 값은  test 모듈의 `__dict__` 속성에 정의된다. ==이 `__dict__` 속성이 실질적인 네임스페이스를 의미하며 모듈의 전역영역을 의미한다.==  따라서 전역영역에서 정의되는 a와 b는 모두 해당 영역에 저장된다.

>[!info]
여기서 말하는 전역영역은 **모듈의 네임스페이스**를 말한다. 변수 a는 test.py라는 모듈의 네임스페이스에 저장되고 모든 모듈 네임스페이스는 sys.modules 딕셔너리에 저장돼 전체 파이썬 프로세스가 종료될 때까지 유지된다.

이제 a를 활용해 b를 할당하는 구간을 살펴보자. 우선적으로 a의 값을 얻기 위해 파이썬은 LEGB 규칙을 따라서 변수에 접근을 시도한다. 파이썬은 일단 변수가 특정한 함수의 내부에 포함되는지 검사하고 이후에는 클로져 영역을 탐사한다. 이후 모듈 스페이스를 확인하는데 a의 경우 모듈 스페이스에 저장되기 있기 때문에 여기서 참조가 발생한다.

따라서 참조 순서를 확인해보면 `test.__dict__["a"]` 를 우선적으로 참조하고 이후 b를 만들어서 `test.__dict__` 에 저장하는 방식이다. 주요한 점은 `__dict__`를 활용해 곧장 접근을 시도한다는 점이다.
만약 외부 모듈에서 참조를 했다면 `sys.modules`를 통해서 모듈 객체를 먼저 획득하고 이후에 접근을 시도할테지만 모듈 내부에서 참조할 경우 모듈 객체에 곧장 접근이 가능하기 떄문에 `__dict__`에 곧장 접근이 가능하다.

마찬가지로 `foo` 내부에서 접근을 하는 경우를 생각해보자. 함수 내부에서는 어떻게 접근을 시도할까? 명심해야 할 것은 파이썬은 항상 `__dict__` 옵션을 활용해 객체에 접근한다는 것이다. 따라서 함수 내부에서 할당하거나 선언한 변수들은 전부 마찬가지로 함수 객체의 `__dict__` 옵션에 저장된다.  따라서 c는 test 모듈 객체의 foo 함수의 `__dict__` 속성에 저장된다. 

흥미로운 점은 a에 접근할 때 발생하는 과정이다. 위에서 파이썬의 참조에는 항상 `__dict__` 옵션이 활용 된다고 했다. 하지만 함수 객체의 dict에는 로컬 변수에 대한 참조만이 매핑 돼있다. 따라서 전역 변수에 접근하기 위해서는 별도의 접근이 필요한데 ==파이썬 함수에는 이를 위해서 `__globals__` 옵션을 활용한다.==

`__globals__`에는 모듈 네임스페이스에 대한 참조가 저장돼있다. 이를 활용해 파이썬의 함수 객체는 전역 네임스페이스에 위치한 변수들에 참조하는 것이 가능해진다. 즉 함수에서 참조가 발생하면 함수는 먼저 자신의 `__dict__` 을 참조하고 이후에 `__closure__`를 참조하고 이 다음 `__global__`를 참조한다. 

따라서 foo에서 a에 접근을 하는 방식은 `a.__dict__["foo"]` -> `foo.__global__["a"]`와 같은 순서로 진행된다. 

>[!info]
> **함수가 모듈 스페이스에 대한 참조를 계속하고 있기 때문에 해당 함수가 어딘가에서 참조되고 있을 경우 전체 모듈 스페이스의 레퍼런스 카운트가 줄어들지 않아 메모리 누수가 발생할 수 있다.** 
>

>[!info]
>파이썬에서 모든 속성은 `__dict__` 에 저장되며 이는 기본적으로 로컬 스페이스이다. 다양한 스페이스 접근을 위해 파이썬의 함수는 `__globals__, __closures__`를 활용한다.

### globlas, nonlocal

globals와 nonlocal 같은 키워드와 이것과 연결된다. 이러한 키워드를 앞에서 선언할 경우 네임스페이스를 덮어쓰는 효과가 발생한다. 특정 함수 등에서 이를 활용할 경우 함수에서 해당 변수는 로컬 스페이스가 아닌 해당 스페이스를 사용하게 된다.

```python
a = 5
def foo():
	global a
	a = 10
	print(a) # 10
	print(foo.__dict__.get("a")) # None
	print(foo.__globals__["a"]) # 10
```
